# VISULIA — 設計案

作成日: 2026-09-27
状態: 2026-09-27、自由編集・持ち込みログ・セッション専用環境を含めユーザー承認済み。実装・実機検証は未実施。

製品名: VISULIA / CLI実行名: `visulia`。npm登録名は小文字の`visulia`を候補とする（取得可否は未確認。必要ならscopeを使用）。

## 1. 目的と合意済みの範囲

外部SaaSへログを送れない企業に向け、社内環境でログ生成・継続収集・正規化・検索・可視化・調査ができることを示す、GitHub公開用ポートフォリオを作る。npmからインストールする対話型CLIを入口とし、環境構築の案内と実行、運用操作まで含める。

- 導入時のインターネット利用は可能。完全閉域への配布は対象外。
- 通常の解析に外部SaaSや外部LLM APIを必須としない。利用状況の自動送信は実装しない。
- 旧VMやインターン時のコード・実ログには依存せず、新規実装する。
- 手元にTomEEログはない。テスト用TomEEにHTTPリクエストを送り、実際に出力されたログを逐次処理する。
- この端末に解析基盤はまだない。CLIで構築する経路と、後から用意した既存環境に接続する経路を設ける。
- GitHub・npmへの公開は成果物と公開先が確定した時点で別途実施する。今回の設計承認は公開操作の承認を意味しない。

## 2. 採用を提案する構成

TypeScript/Node.js製CLIをnpm配布する。利用者に必要なのはNode.js/npmとブラウザーであり、公開デモの利用にDockerやローカルElasticsearchは不要。作者が管理するサーバーにVISULIA APIを構築し、利用者の実行セッションごとにTomEE、Vector、Elasticsearch、Kibanaの専用環境をComposeで割り当てる。CLIはHTTPSでVISULIA APIへ接続する。管理用Compose定義、Parser、Mapping、Dashboardテンプレート、デモアプリのビルド素材は同じリポジトリで管理する。社内自己ホスト用の構築経路も保持する。

```text
利用者の端末: visulia（対話CLI） / ブラウザー
                 │ HTTPS
作者の公開サーバー: VISULIA API / 認証付きブラウザー入口
                 │ セッションごとに独立したアカウント・サービス・保存領域を割り当て
                 ├─ 生成器 → TomEE → Vector → Elasticsearch
                 └─ ES|QL / Kibana API → 利用者専用Dashboard
```


Logstashは基本経路では使用せず、投入はVectorが担う。「ELK」は利用者向けの通称として扱い、実際の構成は明示する。

比較した選択肢:

| 方式 | 利点 | 制約 | 判断 |
| --- | --- | --- | --- |
| npm CLI + 作者のデモAPI | 利用者はnpm導入だけで体験できる | サーバー側に認証とセッション管理が必要 | 公開デモの標準経路 |
| npm CLI + Compose | 社内環境で構成を再現できる | 管理者のコンテナ実行環境が必要 | 作者の構築・自己ホスト経路 |
| npm CLI + 各サービスの直接インストール | コンテナなしで導入できる | OS差・依存関係・削除処理が複雑 | 初回の対応範囲外 |
| 既存Elasticsearch/Kibanaへ接続 | 社内環境を利用できる | 権限・バージョン・TLS設定が環境依存 | 接続経路として対応 |

CLIの初回検証対象はmacOS/Linux。作者のホストはLinux上のDocker Compose v2互換環境、ローカル開発もComposeを使用する。Docker自体がない場合は導入手順を示し、CLIからホスト全体を変更するインストールは行わない。サービスのバージョンとイメージdigestは実装時に公式情報・取得可否・CPUアーキテクチャ対応を確認して固定する。過去のElastic 9.4.4という記録をそのまま採用しない。

## 3. CLIの利用体験

CLI実行名は`visulia`。製品の表示名はVISULIAとする。

- `visulia` / `visulia start`: 公開デモへ接続し、専用セッションを作成。対話で生成デモログまたは持ち込みログを選び、収集、ES|QL検証、Dashboard作成を進める。専用の接続先・認証情報を発行し、その後も利用者が設定と描画を編集できる。有効なセッションは再接続できる。
- `visulia setup`: 作者・自己ホスト管理者向けのCompose環境の準備、または既存環境の接続設定と疎通確認。公開デモ利用者には実行を要求しない。
- `visulia upload <path>`: 利用者が選択したログをセッション専用領域へアップロードし、Parserを選択・編集して検証する。未知の形式も手動のParser定義で試せるが、自動対応済みとは表示しない。
- `visulia template`: 自分のParser、Mapping、ES|QL、Dashboard定義を取得・編集・検証・適用する。共有の雛形はコピーして使い、元の雛形を書き換えない。
- `visulia demo start|stop`: 正常・404・500・遅延のシナリオを選んでログ生成を開始・停止。
- `visulia init`: 入力ログの種類、出力パターン、製品バージョン、環境・サーバー情報を登録。
- `visulia check --offline`: 設定、Parser、サンプル、Schemaを接続なしで検証。
- `visulia check`: 上記に加えて接続先、権限、Mappingの互換性を確認。
- `visulia ingest`: 事前検証を通した設定で継続収集を開始。デモ起動も同じ処理を使用。
- `visulia dashboard`: 受理確認済みテンプレートからData ViewとDashboardを適用し、URLを表示。
- `visulia status|stop`: サービス・収集の状態を確認し、または停止。通常の自己ホスト環境ではデータを保持する。使い捨てデモセッションでは、終了時にセッション所有のリソースを削除する。

各手順で、目的、実行内容、結果、次の操作を表示する。利用者の「実行した」という回答だけで成功にはしない。サービスごとの疎通と必要APIを確認する。失敗時は原因の要約と構造化エラーの保存先を示し、そのステップから再開する。

対話と処理本体は分離し、設定ファイルによる非対話実行も可能にする。非対話で必要情報が欠けている場合は、待機せず明示的に失敗する。

## 4. 入力とデータ契約

最初の実証対象はTomEEのアクセスログ。Tomcatについても同一のAccessLogValveパターンを共用できる設計とするが、TomEEでの成功だけでTomcatを動作確認済みとは記載しない。

少なくとも2種類の出力パターンをfixtureとして扱う。製品名だけで形式・時間単位を推測せず、明示されたパターンと製品バージョンをParser選択の条件にする。ログ本文から得た情報と利用者が与えたmetadataを区別する。

共通Schema v1の提案:

| フィールド | 意味 |
| --- | --- |
| `@timestamp` | リクエストの時刻。UTCへ正規化 |
| `event.original` | 元のログ行 |
| `event.dataset` | ログ種別 |
| `event.duration` | 処理時間、整数ナノ秒。入力にない場合は省略 |
| `http.request.method` | HTTPメソッド |
| `http.response.status_code` | HTTPステータス、整数 |
| `url.path` | リクエストパス |
| `service.name`, `service.version` | 発生元サービス |
| `host.name` | 発生元サーバー |
| `labels.environment`, `labels.scenario` | 解析条件 |
| `log.file.path` | 取り込み元ファイル |
| `analysis.run_id`, `analysis.schema_version` | 実行とSchemaの識別 |

時刻・ログ種別・サービス・環境・HTTPメソッド・パス・ステータス・元ログを必須とする。取得できないユーザー情報や処理時間を推測で埋めない。時刻のタイムゾーンが入力にも設定にもない場合は検証失敗とする。

過去のms統一という方針に対し、この案では保存単位を`event.duration`のnsとし、表示時にmsへ変換する。これは今回の設計提案であり、旧実装の再現ではない。単位の明示とテストを必須とする。

Schemaは型と必須項目を定義したバージョン付き契約として管理し、Elasticsearch Mappingとの整合を検証する。未定義フィールドを無制限に投入しない。同梱Dashboardは共通フィールドを使う。利用者はセッション内でSchemaとDashboardを拡張できる。拡張フィールドを参照する独自パネルの互換性は、同梱テンプレートとは区別して検証する。

## 5. 継続処理と障害時の挙動

- 入力ファイル、読み取り位置、ディスクバッファ、Elasticsearchデータはセッション稼働中の再開に必要なストレージへ置く。通常の自己ホスト環境では保持し、使い捨てデモでは終了後の削除を許容する。
- 起動前の設定・サンプル検証で失敗した場合は投入を開始しない。
- 起動後に到着する不正行は理由・元データ・発生時刻・run ID付きで隔離し、正常行の処理を継続する。事前検証が将来の全行の正しさを保証するとは扱わない。
- 接続断では有限サイズのディスクバッファで再送を待つ。満杯の場合はbackpressureをかけ、状態を明示する。無限に保存できるとは主張しない。
- 配信はat-least-onceを前提とし、exactly-onceは主張しない。デモには一意のリクエストIDを付け、再送時の同一イベントを同じドキュメントIDで扱う。IDのない一般ログの重複排除は保証しない。
- rename方式のログローテーションとプロセス再起動後の再開を試験する。copytruncateは初回の保証対象外と明記する。
- 完全に同じ内容の正当な別リクエストを本文hashだけで消さない。
- 再解析は元ログを保存したデモrunから新しい投入先へ実行する設計とし、既存の解析結果を暗黙に上書きしない。

## 6. デモとDashboard

小さなServletアプリに正常・意図的な500・遅延のエンドポイントを用意し、存在しないURLで404を発生させる。リクエスト生成器はシナリオ、件数、送信レート、run IDと送信結果を記録する。負荷はデモ用TomEEを宛先とし、任意の外部URLには自動送信しない。

Dashboardの導線:

1. Overview: リクエスト件数、5xx率、処理時間の分位点。
2. Trend: 時系列で増加・悪化した時間帯を確認。
3. Breakdown: パス・ステータス・サーバー別に絞り込み。
4. Evidence: 対象の元ログへ到達。

アクセスログだけで内部例外の原因を断定しない。サーバーログとの関連付けは後続の拡張とする。

集計・検索・パネルのデータ取得はES|QLを基準とする。ES|QLはクエリ言語であり、インデックス作成やDashboardの保存・削除までを担う管理言語として扱わない。

- Elasticsearch REST API: Mapping、投入先、取り込み、セッション所有データの削除。
- ES|QL API: クエリの検証、KPIの集計、調査結果の取得。
- Kibanaの対象バージョンでサポートされるAPI: Dashboard/パネルの保存・適用・取得・削除。
- Kibana: 描画と対話的な調査。ブラウザーのローカル保存や独自WebUIをDashboardの正本にしない。

初期Dashboard JSONは対象のKibanaで受理を確認したテンプレートを同梱する。利用者は専用Kibanaにログインし、パネル、ES|QL、レイアウトを自由に編集・追加・削除できる。CLIは変更を暗黙に上書きせず、再適用時は差分と置換範囲を示す。テンプレートのES|QLの参照先置換、ID置換、再適用を検証する。クエリがHTTP 200でもパネル描画を確認できるまでは完成としない。ES|QLパネルで不要なData Viewは作成せず、使用するパネルが必要とする場合のみ追加する。

## 7. データの扱いと公開範囲

ローカルデモの公開ポートは標準でloopbackに限定する。リモートのデモでは認証付きHTTPSの入口を使用し、Elasticsearchの管理ポートをそのまま公開しない。認証を有効にし、生成した認証情報はGitやnpmパッケージ、通常のログ出力に含めない。既存接続先では認証とTLS証明書検証を扱い、検証無効化を既定値にしない。

導入時にアクセスするパッケージ・イメージ配布元と、実行時の通信先を文書化する。自己ホスト構成では外向き通信を遮断した検証で基本のデモが動くことを確認し、「ログの外部送信不要」という主張の範囲を示す。

公開物には新規コード、デモログ、設定例、構成図、README、デモ動画、検証結果を含める。勤務先のコード・実ログ・認証情報は含めない。サードパーティ製品のライセンスと必要な利用条件を明示し、同梱する独自コードのライセンスは公開前に決定する。

## 8. 検証と完了条件

| 検証 | 合格条件 |
| --- | --- |
| npm配布物 | `npm pack`した成果物を空の作業先へ導入し、CLI・テンプレートが動く |
| 設定とParser | 2形式が同じSchemaになり、単位・欠損・不正行・タイムゾーンを検証できる |
| 利用者の初回導入 | Docker/ESなしの端末へnpm成果物を導入し、作者のサーバーへの接続からDashboard表示まで成功 |
| 管理者の構築 | 新しいComposeプロジェクトでサーバー構築・疎通確認まで成功 |
| 分離と回収 | 2セッションで同名のindex template、インデックス、Dashboardを作成・編集しても干渉しない。他方へのAPIアクセスは拒否され、片方の終了でも他方が使える |
| 編集体験 | 利用者アカウントでParser、Mapping、ES|QL、Dashboardを編集し、再解析と描画変更を確認できる |
| 持ち込みと削除 | ログのアップロードから可視化まで動く。正常終了・強制終了後に専用ボリュームと認証が回収され、管理ログに持ち込み本文が残らない |
| 実ログE2E | 生成器の記録、TomEEアクセスログ、投入後のID・件数・ステータスが対応する |
| 継続収集 | デモ負荷1 request/秒で、収集中の追記が60秒以内に検索可能になる。測定環境を記録し、他環境への性能保証とはしない |
| 障害と復旧 | 接続断・収集プロセス再起動・renameローテーション後にデモの一意IDが欠けずに取り込まれる |
| 不正入力 | 不正行が隔離され、正しい行の投入とエラー参照ができる |
| Dashboard | APIで保存を確認し、画面でパネル表示・絞り込み・元ログへの到達を確認 |
| 外部接続不要 | 社内自己ホスト構成において、導入後の外向き通信を遮断しても生成・収集・可視化が動く。公開デモでは作者のサーバーへの通信が必要 |
| 再現性 | 対象OS・CPU・製品バージョン・コマンド・期待値・出力を検証記録へ残す |

画面確認、実サービスE2E、他者による試用を、単体テストやモックの成功で代替しない。他者による試用が未実施ならその旨を公開資料に記載する。

## 9. 実装の分割

1. CLIとAPI契約、対話、セッションごとのアカウント・専用環境の発行と期限管理、構造化エラー。
2. Composeによるサービス準備と、TomEEデモアプリ・生成器。
3. デモ生成と持ち込みアップロード、編集できるParser/Mapping、Vectorによる継続処理、共通Schema、隔離・再開・再送。
4. Elasticsearch/Kibana接続、MappingとDashboard、既存接続先への設定。
5. セッションの分離・期限・削除、npm配布物とリモート接続E2E、障害試験、READMEと公開用の証拠。

各段階は全体を完成させるための実装順であり、機能の選択肢ではない。LLMによる未知ログのParser生成、KPIの自動設計、サーバーログの複数行解析、本番HA構成は、今回の公開デモ完成後の拡張とする。

## 10. npm利用者が体験する最終到達点と終了処理

利用者が自分の端末へVISULIAをnpmで導入し、`visulia`の対話からホスティングされたサーバーに接続し、解析条件を選び、実際のElasticsearch/Kibana上にDashboardを構築する。ブラウザーでDashboardを開き、TomEEの生成ログが反映されることを体験する。

接続先は作者が用意する公開デモサーバーと確定した。利用者はインフラを構築せず、CLIの対話によってサーバー上に自分の解析セッションとDashboardを作る。ローカルComposeだけで最終到達点を満たしたとは扱わない。

サーバー側の追加設計:

- `visulia start`による1つの実行セッションを発行単位とする。同じ人でも新規実行では独立した環境とアカウントを得る。子プロセスごとに別環境を作る意味ではない。有効なセッションの再接続は同じ環境を使う。
- VISULIA APIがセッションID、APIトークン、専用ES/Kibanaアカウントを発行する。利用者は認証付きHTTPS経由で自分のES APIとKibanaを操作できる。ホストや他セッションを管理する権限は発行しない。
- Elasticsearch、Kibana、Vectorの実行環境・ネットワーク・ボリューム・設定をセッション単位で分離する。アカウントやKibana Spaceの分離だけに依存しない。ESのindex/component templateなどクラスタ範囲の設定も自由に変更する要件に合わせ、共有ESクラスタを標準構成にしない。
- 同梱のParser/Mapping/ES|QL/Dashboardは各環境にコピーする。Vector設定の変更は専用ワーカーへ適用する。共有のホストパス、Dockerソケット、他セッションのネットワークや秘密情報を利用者の処理へ渡さない。
- ブラウザーへの引き渡しは短時間・一度限りのチケットを使い、認証付き閲覧セッションを確立する。長期トークンをDashboard URLへ埋め込まない。
- 生成器・収集処理・作業ディレクトリはセッション所有を記録する。共有サービスの停止を利用者へ許可しない。
- 利用者がES|QL、Parser、Mapping、ESテンプレート、Kibanaパネルを変更できる。クエリを提供済み定義だけに限定しない。生成器の負荷対象は専用TomEEとし、ホストのshell実行や他セッションへの操作は提供しない。
- セッションごとにCPU・メモリ・ディスク・入力サイズ・実行時間を制限する。専用ES/Kibanaはメモリを要するため、実ホストの容量を測定して同時起動数を決める。アカウント分離だけで性能競合が消えるとは扱わない。
- 同時セッション数、生成レート、最大稼働時間、ディスク使用量にサーバー側の上限を設ける。上限到達時は新規開始を断り、既存セッションを勝手に削除しない。
- heartbeat間隔は30秒、切断猶予は5分、デモ最大時間は30分を初期案とする。期限切れ後の再接続では削除済みデータを復元せず新規セッションを案内する。
- ホストの台数・メモリに応じた同時実行上限は公開前の負荷試験で設定する。実ホストと公開URLは未設定。

使い捨てデモの終了処理は以下を提案する。

- セッションIDと所有リソースの一覧をサーバー側で管理する。コンテナ、ネットワーク、ボリューム、アップロード、インデックス、Dashboard、テンプレート、作業ログ、認証情報の所有範囲を記録する。
- 明示終了時は新規操作と認証を停止し、生成・収集を止め、専用コンテナ、ボリューム、アップロード、設定、描画定義、一時権限を削除する。利用者の端末にある元ファイルや、共有の管理基盤は削除しない。
- 異常終了・ネットワーク切断ではCLIの終了処理に依存しない。heartbeatとサーバー側の期限管理で回収する。猶予時間の初期提案は5分とし、短時間の切断は復帰可能にする。
- 削除は再実行可能にし、途中失敗を記録してサーバー側で再試行する。切断直後の削除完了は保証しない。
- ローカルCLIにはDashboard本体や解析データを永続保存しない。再接続に必要な最小のセッション情報を使い、終了後は一時認証情報を削除する。
- ブラウザーのタブを閉じることと、CLIセッション終了は区別する。Dashboardを閲覧中はCLIセッションを維持する。
- セッション間の参照・更新・削除ができないこと、正常終了と強制終了の両方で期限後にリソースが回収されることを検証する。

ログがない利用者には生成デモログを提供し、ログがある利用者にはアップロードによる試用を提供する。アップロードするファイルと接続先は利用者が選ぶ。CLIはローカルのログを勝手に探索・送信しない。

「保存しない」は、処理中にもデータを保持しないという意味にはしない。ESのインデックス、アップロード、隔離ログ、バッファ、編集した定義はセッション中だけ一時保存し、終了・期限切れ後に削除する。セッションデータはバックアップ/スナップショット対象外とし、管理ログ・リバースプロキシログに持ち込み本文や認証情報を記録しない。障害時の削除再試行に必要なリソースID・削除状態は内容データと分離する。基盤のディスクからの即時の物理消去までは保証しない。

公開デモへの持ち込みは作者のサーバーへの外部送信であることをCLIとREADMEに表示する。外部送信できないログを扱う企業向けには、社内自己ホスト構成を提供する。

## 11. 設計レビューで確認する提案

ユーザーから指定されていない実装上の提案は、TypeScript、作者側のDocker Compose、VISULIA APIとセッション認証、切断猶予5分と最大稼働30分、最初のログ種別をアクセスログとすること、保存時間単位をnsとすること。これらを含む本書を確認後、具体的なファイル構成・作業順・テスト手順を実装計画へ落とす。
